# Design: the browser course

The decisions behind the course site, as agreed during planning (2026-10-16). It borrows from the Temporal loan-origination course (`temporal-training-agentic-loan-origination/course`): its look, its Vue + Vite site, and its runner's Temporal UI proxy. Read this before changing what the site is for or how the runtime works.

## What it is

- **A course site with a browser runtime.** Anyone can see the map; signed-in learners read the modules and get a cloud sandbox to do the exercises in (Accounts, below). Running locally stays first-class: the setup page covers it, and exercise pages show the local instructions when the runtime is off. The mode is no longer a choice (a Browser | Local switch was replaced by **↺ Start over** in the guide's header): with the runtime available, it's the browser.
- **One source of truth.** The site is generated from the workshop: the modules in `quests/` (their frontmatter gives title, teaser, time, files and tour; a path groups them into the exercises the site shows), the README (home and setup pages), and `starter/` and the `authoring/` masters (the editor). Nothing is copied by hand. The instructor notes, DESIGN.md and the authoring docs aren't on the site.
- **Mode blocks** in the modules: browser-only text sits inside `<!-- browser … -->`, so GitHub doesn't show it, and `<!-- local -->…<!-- /local -->` marks local-only text. The build also turns `localhost:8000`/`:8233` links into pane links in the browser.
- **The look is the loan-origination course's**, token for token, in light and dark, so the two read as one family. The embedded console and Temporal UI keep their own styling; the site frames them.
- **Learner niceties**: a guide that takes you through one step at a time (below), a passed badge and confetti when an exercise's check passes, light/dark, and a first-visit tour.

## The runtime

- **One sandbox per learner, for the whole workshop**, like running locally: the stack stays up across exercises, `setup.sh`/`solve.sh` move the code between stages. It stops after 30 idle minutes and is started again on the next visit (the loan course deletes and recreates instead); it's deleted 24 hours after creation.
- **Found by label, not remembered.** A sandbox carries `app=governance-course` and `learner=<id>`; the runner looks it up, so its own state (terminal buffers, preview URLs, rate limits) is a cache that a restart only costs a moment.
- **A start can't spin forever.** Every Daytona call the runner makes has a timeout, listing sandboxes too (30 s), so a Daytona that doesn't answer turns into an error with Try again. If a step still takes much longer than it should (20 s to find the sandbox, 90 s for anything else), the page offers **Check again** and **Start over with a new sandbox**. Starting over cancels the run in progress on the runner (it stops reporting progress, and a sandbox it was creating is deleted when it arrives) and starts a new one. Signing in from Ask Temporal looks the sandbox up as loading the page does; before, it left the panes on "Looking for your sandbox…".
- **A dependency-only snapshot.** Python, uv, the synced `.venv`, the Temporal CLI, the dev server the pytest checks download, and Dogwood's CLI and verifier built for Linux (`scripts/setup_dogwood.sh`, unchanged, in a Rust stage). The workshop's files are uploaded again when a sandbox is created and switched to the starter, so a content change needs a deploy, not a snapshot. The snapshot's name is a hash of its inputs, so a deploy can't silently use stale dependencies.
- **`travel-stack up` runs when the sandbox starts**, with `TRAVEL_STACK_BIND=0.0.0.0` (the one change to `travel_agent/stack.py`) so Daytona's preview proxy can reach the Temporal UI. Stale pid files are removed first: a sandbox that stopped and started again would otherwise look like it was still running.
- **Real terminals, and buttons that type into them.** Two Daytona PTY sessions, `worker` and `commands` (it was `shell`, which said what it is rather than what it's for), bridged to xterm.js over WebSockets. The exercises are about stopping and restarting a worker, so that has to be real. The worker toggle, Check, ▶ on snippets, and Solve all type into a terminal, so learners always see what a button did. The worker terminal gets a Ctrl-C first.
- **The editor writes to the sandbox**, which holds the real copy: the exercise's TODO file is editable, related files are read-only, and a file changed on disk (by `./quest` or the terminal) reloads, or asks when there are unsaved edits. No type checking (the loan course's was TypeScript-specific).
- **A language server for the Python files**, so hovering shows a symbol's signature and docs, F12 or Cmd/Ctrl-click goes to its definition (opening that file's tab when the exercise has one, and otherwise peeking at it: the file and line, the signature and the docs, at the cursor), and completion comes from the real `temporalio`. It's jedi-language-server in the sandbox, in its own venv (`/opt/lsp`) pointed at the workshop's: light, and it reports syntax errors but not type errors, which would cover the TODO stubs in red. `lsp_bridge.py` serves it over a WebSocket with one server process per connection, so two tabs don't share one server's open files; the runner relays it at `/api/lsp` through the sandbox's preview URL, starting the bridge if it isn't answering. Hovering a keyword argument (`start_to_close_timeout=`) explains it: jedi only knows its type, so the bridge answers one request of its own, `course/paramDoc`, finding the text in the library's docstrings (the function's "Args:", or the function its docstring points to, as `execute_activity`'s points to `start_activity`; or the docstring under a dataclass field, as `RetryPolicy`'s). The hover also has an Ask Temporal button, which opens the helper with the question and the line, for more or for an argument the docstrings don't cover; it's a button, not automatic, so hovering doesn't spend model calls. Only your copy gets it while the sandbox is live; the solution view and Local mode don't. Rename and formatting are left out, since they'd edit read-only files.
- **Passed checks leave a marker** (`.course/passed/<exercise>`, written by `./quest check` when it succeeds), which the page polls. Locally it's harmless and git-ignored.
- **Layout: two columns.** The top bar is Previous / picker / Next / Tour / theme (the overview and setup pages are in the picker). The workspace is on the left: tabs for **Code** (file tabs with the solution switch, the editor, a lines/chars footer), **Harness** (the agent harness's console) and **Temporal UI** (each a long-lived iframe, only hidden behind another tab, so it never reloads), and in exercise 3 **Trip briefing** (the travel team's form, loaded the first time its tab opens; its workflow link opens the Temporal UI tab), over a dock with the terminals (the worker toggle and Check in its bar). The guide is on the right. (It was three columns, the console and the Temporal UI in a pane that slid out beside the instructions; at 1440px that left the instructions about 280px. One view at a time at full width reads better, and the terminals stay in sight under every view.) The guide brings the tab a step needs forward when you arrive at it: Code for a step with an Insert button, else the console or Temporal UI it links to, else the console if it talks about it, else Code if it names one of the exercise's files; and inserting a snippet, opening a file or the code tour bring Code forward, as a Temporal UI link or a trip's Open bring the Temporal UI. The tab bar has the view's reload and open-in-a-new-tab, and an expand button (or a double-click on the bar; Esc puts it back) that lays the workspace over the guide's column too.
- **One worker toggle, everywhere.** Wherever the instructions say to stop or start the worker, and in the dock, the same control shows whether a worker is running (the sandbox poll checks the process, so typing `uv run travel-worker` counts too) and stops it with Ctrl-C or starts the exercise's worker, visibly, in the worker terminal. It reads "starting…" or "stopping…" until the poll confirms.
- **Code from the instructions into the editor.** A snippet meant for the exercise's file has **← Insert into …**: it replaces the TODO block when the snippet solves it (the build reads the block from the authoring masters' markers, so it's exact), appends a policy rule that isn't the TODO, or goes at the cursor. The new lines flash, the editor scrolls to them, a toast says which lines, and they save like any edit. While the snippet is in the file (as written, indentation aside), its button reads **✓ In … · Revert**, which brings the TODO block back or removes the appended rule; the button follows the file's text, not its own clicks. The snippets are commented on their key concepts, since they end up in learners' files.
- **Commands in prose run too.** Inline code that's a command (`uv run …`, `temporal …`, `./quest …`, `cat …`, with no placeholder) gets a ▶, like a code block's.

## Proxies and security

- **The console** is proxied under `/sbx/console/` on the site's origin: its page uses relative paths, and it streams over SSE, which passes straight through.
- **The Temporal UI** needs an origin of its own (root-absolute paths), so it's on the runner's second port, same host. The loan course's proxy is reused: it strips the framing headers and CSP, rescopes cookies, injects a loading overlay and a postMessage bridge for client-side navigation, and caches the UI's hashed assets across learners.
- **Access**: a signed-in user's random id, with the time they signed in, signed into an HttpOnly cookie (14 days from sign-in). The cookie reaches the UI proxy's port because cookies ignore ports. Every sandbox operation goes through the learner's own id, so nobody can drive someone else's sandbox (the loan course accepted any sandbox id). At most `MAX_SANDBOXES` (40) run at once.
- **The model**: Gemini, through a passthrough in the runner rather than LiteLLM. Gemini 3 sends each tool call's thought signature (`extra_content`) and needs it back on the next turn; a translating proxy risked dropping it. Each sandbox gets its own key, signed from its learner id and valid only on `/llm/v1`; the model is pinned; 20 requests a minute per sandbox and 300 overall. A learner can read their sandbox's key (it's in `.env`), and that's fine. A scripted-model toggle covers Gemini misbehaving.
- **Admin view**: `/admin`, for `ADMIN_EMAILS` (Accounts, below).

## Accounts (added 2026-11-10)

The site is for on-demand training as well as live events, so learners have accounts. Decided in `.scratch/temporal-quest/` (issues 04a–04f).

- **Email and a code, not a password or OAuth.** A learner enters their work email and gets a 6-digit code (Resend), good for 10 minutes and once; 5 wrong tries use a code up, and 10 wrong codes an email in 15 minutes lock it for the rest of that time, however many new codes are asked for. A code rather than a magic link: at a workshop the email is often read on a phone while the sandbox is on a laptop. Sends are limited to 3 an email and 10 an address per 15 minutes.
- **The session is a signed cookie, checked against the database.** `userId.issuedAt.sig`, 14 days from sign-in, not sliding. Every request looks the user up in SQLite (cheap: one machine, one file), so blocking someone or taking them off the allowlist signs them out at once, which a cookie alone can't. Rotating `SESSION_SECRET` signs everyone out.
- **The email stays in the runner.** Each user has a random id, which labels their sandbox and signs its model key, as the anonymous learner id did; Daytona never sees an email.
- **The allowlist decides who's in.** Exact emails and domain rules (`@acme.com`), each in a **cohort** (a name, an optional path, an optional end date, a daily sandbox allowance). An exact email wins over a domain rule, which is how a learner is moved to another cohort. `ADMIN_EMAILS` are always in. A local runner without `RESEND_API_KEY` prints codes to its console and lets any email in, to requests addressed to localhost only.
- **Company emails can ask; personal ones can't.** A free-mail address (a fixed list in `accounts.mjs`) is asked for a company one, unless the allowlist has it exactly. A company email that isn't listed still gets a code, so a request is only ever filed by the address's owner; then name and role file the request. Admins are emailed; they approve the one email or the whole domain into the built-in **On-demand** cohort, or reject it with a reason, and the learner is emailed.
- **The map is public; the modules aren't, softly.** Module text stays in the bundle and the repo stays public: the sign-in is for knowing who's learning, not for secrecy.
- **The activity log is append-only events** (`events`): the server records sign-ins, codes, the sandbox's lifecycle, helper questions, model-call counts a minute and admin actions; the page sends modules opened and passed, challenge picks, boss results and the path it chose. Progress is derived from the events, so it follows a learner across browsers; what a browser had before the learner's first sign-in is imported then, once.
- **Heartbeats, not events, for time on a module.** A visible module page says which module it's on once a minute. That moves a "last seen on X since T" row and adds to the learner's time on X (at most 90 s a beat), so a hidden tab or lunch doesn't count, and "stuck" means on one module for 10+ minutes without passing it, and still there.
- **Sandbox time against an allowance.** Once a minute the runner lists the sandboxes; a running one counts a minute for its learner (idle time before Daytona's auto-stop too: Daytona bills for it). The sum over any 24 hours is held to the cohort's allowance (8 hours unless set). Ten minutes before, the learner is warned; at it, the sandbox stops and won't start until enough time has rolled out of the window. There's no daily cap on model calls: sandbox time bounds them, with the per-minute limits.
- **Deleting a learner** removes their user, events, allowlist entry and sandbox, and their email from the admin log.

## Ask Temporal (added 2026-10-17)

A helper for questions about Temporal, in a panel at the right edge of every page (⌘K / Ctrl+K, or the top bar's button).

- **The docs are the source of truth, through Kapa.** Temporal's docs search is Kapa's hosted MCP server (`https://temporal.mcp.kapa.ai`). Kapa only retrieves: its `search_temporal_knowledge_sources` tool returns ranked chunks (a source URL and Markdown). So the runner's Gemini writes the answer: a short tool loop (`runner/helper.mjs`) where the model gets one tool, `search_temporal_docs`, must search on its first turn (`tool_choice: "required"`; models like to skip it), may search again (at most 3 searches, 4 model turns), and cites what it used as `[n]`. The answer streams to the page as server-sent events: search steps, sources, text.
- **Each learner verifies with Kapa, once.** The public server asks every user to prove they're human with GitHub or Google (OAuth 2.1 with dynamic client registration and PKCE). Sharing one learner's token with the room would defeat that, and put everyone on one user's limits (600 searches a day), so each learner connects their own, in a popup that hands back to the page with `postMessage` (or a full-page round trip when popups are blocked). The token is sealed (AES-GCM, from `SESSION_SECRET`) in an HttpOnly cookie on `/api/helper`, so it survives a restart and the browser can't read it. An instructor with a Kapa API key for Temporal's project sets `KAPA_API_KEY` instead, and nobody connects anything.
- **It knows where you are.** The prompt carries the exercise's assignment in your mode (from the build's `assignments.json`, read by the runner, so the page can't swap in a different one), and, unless you untick its chip, the file you have open in the editor. A selection from the instructions, the editor (CodeMirror's) or a terminal (xterm's) goes with the question, with quick questions for each ("What does this error mean?"). It's told that Monty, Dogwood and the harness are the workshop's, not Temporal's, and to hint before handing over a TODO's solution.
- **Kapa's limits are shared, so searches are scarce.** Kapa allows 60 searches a minute across all its users. Results are cached by query for 30 minutes (the docs are public, and a room asks the same things), the runner holds itself to `KAPA_RATE_GLOBAL` (50), and a search that can't run says so in the answer rather than failing it.
- **Gated like the runtime, but not on it.** The helper needs `GEMINI_API_KEY` and a signed-in learner, not Daytona, so a learner working locally can still ask. Signed out, it shows how to add the same docs server to Claude Code, Cursor or VS Code instead.
- **It sits beside the work.** On a wide screen the page makes room for the panel (no backdrop), so you can keep selecting things to ask about; narrower, it covers the page. Its Markdown and highlighting load the first time it opens. The conversation stays in the browser (`localStorage`), and answers render with no raw HTML.

## The guide (added 2026-10-17)

The instructions pane is a conversation with a guide (✦, the same mark as Ask Temporal) rather than a long page.

- **One beat at a time.** The intro, each `##` section of the assignment, the stretch and the check are beats, in the assignment's order. Only the current one is shown, as the guide's message, with a short lead-in ("Nice. Next up:") and its own heading ("Step 3 of 7 · Call the activity"). Earlier beats fold into a trail you can open and click back into; later ones aren't shown. The progress bar's segments jump to a step.
- **Quick replies move it on.** "Let's start", "Got it", "Done, next step" (which ticks the step) and "← Back". The last beat offers the next exercise. Where you are is remembered per exercise (`guide:<exercise>`), so a reload, or the full-page round trip to Kapa's sign-in, puts you back on the same step. Ticks are kept as before (`steps:<exercise>`).
- **Questions go to Ask Temporal, about the step.** The composer under the guide asks the helper, with the step's title sent as `context.step` so the model knows which part of the assignment you're on (it already has the whole assignment). The answer shows under the step, with the same searches, citations and sources as the panel (`AskMessage.vue` renders both). The guide's questions are a thread of their own (`helper.guide`, each message tagged with its exercise and step); earlier turns from the same exercise go with a question, since its steps build on each other. A step with no questions yet offers a few to tap (the exercise's suggested questions on the intro).
- **The panel stays.** ⌘K and selections still open the Ask Temporal panel, with its own thread. Both share the one connection to the docs, and a question waiting on Kapa's sign-in is asked again from whichever thread asked it.

## In the exercises (added 2026-10-17)

- **The workers load workflow code once, at start.** The Python SDK's sandbox re-imports a workflow's module from disk whenever it rebuilds the workflow (after a failed workflow task, say), so a stuck workflow picked up an edit to `workflow.py` about 7 seconds after it was saved, without the restart exercise 1 is about, and, from an editor that saves as you type, half-typed code. Each worker passes its own package through the sandbox (`hello`, `travel_agent`, and `annotated_types`, which pydantic imports late), as a production deploy would behave. The cost: the sandbox's determinism checks don't cover those modules, which no exercise relies on.
- **Trip buttons.** Exercise 1's `uv run hello-start …` is a button like the worker toggle. The poll lists the latest `HelloTripWorkflow`s (`temporal workflow list -o jsonl`, only for an exercise with trip buttons) and whether a `hello-start` still waits in the commands terminal, which gets a Ctrl-C before another trip starts there.
- **"Temporal UI" is a link** wherever the instructions send you to it, opening the pane where it is.
- **A code tour per exercise**, a card over the editor that spotlights one chunk at a time (other lines fade; the editor gains room at the bottom so a last chunk scrolls clear of the card). The guide offers it at the end of the exercise's briefing, just before step 1, or after the beat an exercise's `tourAfter` names (exercise 2: after "The agent", so the tour shows the agent's approval posture and activities just before the agent starts; Code Mode and Monty come later, as step 6); it steps with → and ←, skips with Esc, and has ✦ Ask for the chunk.

## End-to-end tests (added 2026-10-18)

Playwright, in `course/e2e/`, against the deployed site (the live Fly app unless `E2E_BASE_URL` says otherwise). They test what a learner gets, not the code: the unit tests in `course/tests/` stay the place for the runner's logic.

- **Three tiers, by tag.** `@public` needs no secrets: the `/api`'s answers to a signed-out visitor, the map, the setup page, and a module page's sign-in. `@auth` signs learners in with `E2E_SIGNIN_KEY` and stops short of a sandbox (a signed-in page's sandbox calls are stubbed): every module page, a challenge, Next and paths, Ask Temporal, sign-in through the page, an access request, and the admin. `@sandbox` is a learner's whole run in one real Daytona sandbox: sign in through the page, start it, both terminals, the Temporal UI and Agent UI panes, then **every exercise done the way its instructions say**, ending with its ✓ Check (below). Its sandbox is deleted at the end, pass or fail. A tier whose secret is missing skips rather than fails.
- **When they run.** Every day at 14:00 UTC, every tier, emailed whatever the result (`.github/workflows/e2e.yml`). After every deploy, on what was just deployed (`deploy.yml` calls it), emailing only a failure: every tier when anything a sandbox runs, the runner that drives one, or the site changed (the paths are in `deploy.yml`'s `e2e-scope` job), `@public` and `@auth` otherwise. And when the tests change.
- **The email goes through Resend's API**, sent with `curl` from a message `scripts/summary.mjs` writes, rather than through Resend's SDK or a third-party action: nothing to install, and nothing outside this repo and Resend sees the key (`RESEND_API_KEY`, a repository secret). The same script writes the job summary; the HTML report, traces, screenshots and the terminals' text on a failure are the run's artifacts.
- **The tests sign in without a mailbox.** Their addresses (`e2e+…@temporalquest.dev`) get no email: the runner derives their code from `E2E_SIGNIN_KEY`, and so do the tests. They skip the send limits (wrong codes are still limited per email, so the fixed code can't be guessed). Their admin (`E2E_ADMIN_EMAIL`, one of the app's `ADMIN_EMAILS`) puts each test's new learner on the allowlist, in an `E2E` cohort, and deletes it after, so the tests leave nothing behind. `E2E_SKIP_SANDBOX=1` (a repository variable) keeps the sandbox tier off during an event, where its sandbox would count against `MAX_SANDBOXES`.

### Keeping them in step with the workshop

The `@public` and `@auth` tiers read what they can from the deployed site instead of repeating it: the pages are the picker's, and nothing about an exercise's content is asserted.

The sandbox tier is the exception, on purpose (changed 2026-10-18; it used to run each exercise's `solve.sh` and press ✓ Check, which tested the solutions but not the instructions). **Each exercise is a walkthrough** (`tests/walkthroughs.mjs`, in the words of `tests/learner.mjs`): its assignment, step by step under the step's own title, through the page as a learner uses it. That means the guide's Insert, ▶ and worker buttons, New session and the messages to send, the editor's cursor, both terminals, and the Agent UI's approval cards and trip form. Each step checks what the assignment says will happen, and ✓ Run the check comes last. So an instruction that doesn't get a learner there (a missing button, a step out of order, a TODO the snippet doesn't fit, a check the steps don't pass) fails the run, and a mismatch the page can't follow as written is noted in the report.

- **The real model.** The sandbox's agent runs on Gemini, as for a learner, so the agent's next move isn't fixed. `converse()` answers whatever comes (an approval card, the trip form, a reply) until the turn is over, which it reads from the session's `agent_status` query through the console's own API (`turn_active`): the screen can't say, since the composer stays enabled and State flow's badges keep animating. The walkthroughs assert what the system guarantees (the bookings ledger, which calls waited for approval, what the worker logged), never the model's words. When the agent doesn't act on a request (Gemini sometimes ends a turn with no reply), the walkthrough says what a learner would, once ("Please go ahead and do it now."), and notes the nudge in the report, so a step that keeps needing one shows up.
- **Independent exercises.** Each walkthrough starts with the guide's ↺ **Start over**: a new sandbox, its first poll catching up what the exercise builds on (`./quest catch-up`), so it starts the same way whatever ran before, even when an earlier walkthrough failed. The tests run in order as one learner, and a failure doesn't stop the rest: the next test's new worker signs in as the same learner (its cookies are kept in a temporary file for the run) and finds that learner's sandbox, and the global teardown deletes it. The Agent UI smoke test runs after the walkthroughs: opening a later exercise catches up the earlier ones (the poll's `./quest catch-up`), which just before exercise 1 races its Start over.
- **New exercises are noticed.** A test fails when the picker's exercises aren't exactly the walkthroughs', so an exercise added or removed needs its walkthrough added or removed.
- **Not driven** (each is commented where it'd be): the Temporal UI's Queries tab in exercise 1, and the Agent UI's side panels.

What the tests do depend on is a short contract. **A change to any of these updates `course/e2e/` in the same change:**

## Verified (2026-10-16)

With a real Daytona snapshot and the runner and site running locally (the model behind an ngrok tunnel):

- A new sandbox is ready about 14 s after the code is entered (create, upload, starter, `travel-stack up`).
- Exercise 1 in the browser: the ▶ buttons start the worker and the starter, the worker shows the TODO error, the fix typed in the editor saves to the sandbox, restarting the worker finishes the waiting workflow, and Check passes and marks the exercise.
- The Temporal UI and the console render in their panes; the console's live session state streams through the proxy.
- Exercises 1 to 4 solved with the Insert buttons alone: each TODO replaced in place (indented to fit), saved to the sandbox, its check passed. A second Insert doesn't duplicate; a closed pane is parked off-screen.

## The skill tree (added 2026-11-07)

The front door is a map of every module (`MapPage.vue`, `SkillMap.vue`), and the exercise picker is gone. The plan is `.scratch/temporal-quest/spec.md`.

- **A tree, drawn by hand in SVG, every node named.** The tree reads top down, the way you learn it: Fundamentals is the trunk across the top (tier I left to right, tier II back below it, its boss at the end: a capstone and test-out, not a gate). The specializations hang below as tinted columns (their `column` in `branch.md`), a node and its name a row, the branch's boss at its foot. A line is a prerequisite within a branch. Each column's header says what it opens after ("Opens after F7", Nexus "after A4", AI SDLC "after A7"), and limbs run from a "Specializations open after F7" junction to the columns that open after the trunk. The map is as tall as it needs to be: names stay readable instead of the tree shrinking to fit a screen. Narrower than 1100px the rail goes above it; narrower than 860px the tree is an accordion of branches and tiers.
- **A focused view for beginners (redesign 2026-11-09).** Until F7 is done the map opens focused (`FocusMap.vue`): Fundamentals' tier I as a trail of named steps, tier II summed up in a line, then the five specializations as cards (what each is, how many modules or Coming soon, what it opens after). Focus | Full map switches; the choice is kept (`map-view`).
- **One rule, said the same everywhere: prerequisites are recommended, not required.** Any playable node can be entered; skipping ahead fills in the code it builds on (`./quest enter`). The map's rule line, the legend, the detail panel ("Doing F7 first is recommended, not required. Skip ahead to A1…"), the focus view's "Where it leads" and the Path menu ("None: your own order") all say it, and nothing is drawn as a gate.
- **Four states, and Coming soon apart.** Next (purple fill, a white dot: you are here; what Start opens. The play mark is the Start button's alone, in the same purple, so the page has one call to action), Available (a bright outline in the branch's colour: what it builds on is done), Completed (green, a check), Locked (subdued, a lock: what it builds on isn't done). One glyph (`NodeGlyph.vue`) draws them on the map, the trail, the list, the legend and the panel. Coming soon is content availability, not progress: a dashed outline over whichever state it is, a tag in the panel, and no Start.
- **Selecting a node answers four questions.** A click (or Enter) selects; it doesn't navigate. The rail's panel (`NodeDetail.vue`) shows the selection (the next node, to begin with): what you'll learn (the module's `learn:`), what you'll do (its `teaser`), how long (minutes, XP), and what to do first (its prerequisites, each done or not, and how many more are behind them), then one action: Start, or for a locked node "Start with F1" and a Skip ahead link. ## Challenges (added 2026-11-07)

A challenge (issue 08) tests a module by running it: 3–4 versions of the code the learner just wrote, one right. Each is a node like a module's (a circle; a ⚡ inside while it's available) on the map, on the line between the module it follows and the one it gates.

- **Predict, then run.** Picking a choice shows its code: the whole block, not a diff, since the right choice is often the learner's own code and a diff would show it. **Lock in and run it** records the pick before anything runs, so nobody can try them all for free: 20 XP for a right first pick, 10 for a second, 2 after that.
- **Real runs, in the sandbox, where you can see them.** Picking a choice types it into its file in the editor, with the snippet animation. **Lock in** types `./quest challenge FC1 B --run X` into the commands terminal, and the card reads the same run's JSON lines (`.course/challenges/FC1-B.jsonl`, whose first line names the run, so an older run's lines don't count). As soon as the run's workflow starts, the Temporal UI opens on its Event History, which fills in as it runs: the result is something to see in Temporal, not only in the card. At the end it moves to the workflow the scenario points at (`focus`: FC3's stuck hold), and **Open its Event History** goes back to it. The scenario runs on its own copy of the code and its own task queue, so the learner's worker carries on. A wrong pick comes back out of the file, putting back whatever was there, TODO and all, without taking the view away from the history. Without a sandbox, the card shows the choice's code and plays the committed recording, sped up to at most about 5 seconds.
- **A wrong pick teaches.** It's struck out, with its timeline, the events that matter, an explanation, and **Ask Temporal about this**. After two misses comes the hint. After the right pick, every choice's run is listed together.
- **A beat of its exercise, for now.** Until modules have pages of their own (issue 03), a challenge is a beat of the exercise its module is in, right after that module (before the exercise's Check), and `#/module/FC1` opens it there.
