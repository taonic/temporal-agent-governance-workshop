# Design: Governed Agents With Temporal, Monty, And Dogwood

The decisions behind this workshop, as agreed during planning (2026-10-14/15). Read this before changing the scenario, the exercise order or the architecture. The agenda it implements is [agenda.md](agenda.md).

## Audience and format

- **Who:** AI engineers who are new to Temporal. Policy content stays concrete: edit one rule, not policy theory.
- **How long:** 4 hours with an instructor: 4 exercises of 30–40 minutes, and exercise 5 as a bonus for those with the time (see the agenda). It must also work self-paced, so each assignment carries the explanation the instructor blocks give; `instructor/` has talking points and demo scripts.
- **Style:** one graded TODO per exercise. The extra time goes to guided run / observe / break steps, so it never becomes a race.
- **Platform:** local, or in the browser: the [course site](course/DESIGN.md) runs each learner in a Daytona sandbox, generated from these same modules. Instruqt was dropped as a target (2026-11-07): the content is 5-minute modules in `quests/`, which its one-challenge-per-exercise model doesn't fit, and `./quest` replaced the per-exercise lifecycle scripts.
- **Naming:** "Monty" is the workshop's umbrella name for the agent stack, as in the agenda. In code: the Temporal Agent Harness, running a Code Mode agent whose scripts run in the pydantic-monty sandbox.

## The arc

Make it run (exercise 1), make it durable (2), connect it to other teams (3), make it safe (4), then make it autonomous (5); then attack it (6). One agent, one worker, one console entry throughout; the exercises change the TODO files and the session's **approval posture**:

| Posture | Exercise | What runs without asking |
|---|---|---|
| `dangerously_skip_all` | 2, 3 (default) | everything: "it booked without asking you" sets up exercise 4 |
| `human_approval_only` | 4 | nothing: the noisy baseline |
| `approve_bookings` | 4 (TODO) | the script, lookups, board, notes, trip form, the concierge's answers; bookings (table reservations too) wait |
| `auto_mode` | 5, 6 | the script, lookups, board, notes, trip form, the concierge's answers; each booking as the Dogwood policy decides; one it doesn't permit comes to you (`@on_deny("escalate")`) |

The posture is chosen on the session's start form (`@agent.init` data) and can be changed with the `set_approval_policy` message.

## Architecture decisions

- **The harness is a uv git dependency pinned to `15da54e`.** `dogwood_evaluator` isn't released yet. Move to the PyPI release once it ships. If that branch is force-pushed, the pinned commit may eventually be garbage-collected; vendor it then.
- **The model is any OpenAI-compatible endpoint, not Gemini.** The example's hand-written loop is kept (model call, then each tool call through `runner.run_tool`, which is where approval and Dogwood happen), with the Gemini client replaced by a `call_llm` activity. It streams the reply into the session through the harness's activity-side publisher (`AgentWorkflowRunner.publisher_from_activity`): `reply_delta`, `tool_requested`, `model_interaction_started/ended`.
- **Gemini works through its OpenAI-compatible API** (`gemini-3.8-flash`, the model in use for now). For Gemini's endpoint the key comes from `GEMINI_API_KEY` if set, since a generic `LLM_API_KEY` in a shell is often another project's. Gemini 3 requires each tool call's thought signature back on the next turn: it arrives as `extra_content` on the tool call, and the workflow sends it back with the conversation.
- **The live model is a shared vLLM endpoint on a Daytona GPU** (`scripts/gpu_endpoint.py`, ported from the sandbox workshop), starting with Qwen3.5-9B FP8. `scripts/bench_llm.py` measures whether it can drive the walkthroughs (write the scripts, ask for the form, fall for the injection); move to a larger model if it can't.
- **`LLM_MODE=scripted`** plays a fixed travel agent through the same activity: the checks use it, and it's the live fallback. It covers every walkthrough in the assignments, including the injection.
- **No Jev/TypeSafe script classifier** (`script_classifier=None`): it was one more paid key and fed only the `no-runaway-scripts` rule, which is dropped. Nor any script rules: auto mode pre-approves the script tool, and the policy judges each travel call it makes.
- **Dogwood runs live on the Nexus verifier** from `02strich/temporal-untrusted-workers` (branch `nexus-command-verifier`, commit `2d52ae2`), the design the borrowed example uses. The verifier is a separate service with its own durable store, which makes a good point in itself: the agent can't touch the policy or the history. The alternative considered was the harness's "Playpen" (an in-process activity that shells out to `dogwood replay`, on branch `playpen-dogwood-policy`), which needs fewer moving parts but no travel agent existed for it.
- **Exercise 5 is graded offline** with the `dogwood` CLI (1.1.0 from crates.io): `tests/dogwood_trace.py` writes each scenario as the events the verifier records (checked against the verifier's own logged history) and replays them through the learner's `policies/travel.dw`. No Temporal, model or verifier needed. The live verifier embeds `dogwood-language` 1.0.0; both accept the policy.
- **`scripts/setup_dogwood.sh`** builds both Rust binaries at pinned versions into `.dogwood/`. It's learner pre-work; the browser course's snapshot bakes them in.
- **`travel-stack`** runs everything but the agent's worker in the background (Temporal, the Nexus endpoints, the verifier, the concierge's worker, the session manager, the console), so learners only restart the process they're meant to kill. It starts its own Temporal with `history.workflowTaskRetryMaxInterval="5s"` (a fixed bug resumes within seconds), or reuses one already listening.
- **Exercise 3's other team is a second namespace, reached only over Nexus** (`concierge/`, namespace and endpoint `concierge`). Its service has two workflow-backed operations (`nexus.temporal_operation` returning `client.start_workflow(...)`, ids from the Nexus request id), so an operation lasts as long as its workflow: `ask` starts `ConciergeAgent`, an agent, and `reserve_table` starts `TableReservation`, a plain workflow, which is the agent-vs-workflow contrast the exercise is about. `ConciergeAgent` is a plain model-and-tools loop rather than a harness session on purpose: the harness's agent-to-agent path (subagents) is child workflows in one namespace, and a session's reply arrives on its stream, not as an Update's result, so it can't back a Nexus operation without an extra relay; a one-shot agent workflow can, and shows that callers can't tell how the other side is built. On the travel side the two tools are inline `agent.tool_defn`s (a Nexus call is workflow code) offered as Code Mode host functions: `ask_concierge` is `inherently_safe` and in `PRE_APPROVED_TOOLS`, so exercises 4 and 5 don't change; `reserve_table` is gated like a booking, and in the Dogwood schema, where no rule permits it, so auto mode refuses it ("nothing runs by default"). `TripBriefing` (in `default`, on the travel worker) is the workflow-to-agent caller. The concierge shares the workshop's model settings, and has its own scripted model for the checks. `travel-stack` starts its dev server with `--namespace concierge`, creates the namespace on a server it didn't start, creates the endpoint, and runs the concierge's worker as a service learners stop and restart (step 4: another team's outage).
- **The console gets its own session-manager workflow** (`travel-session-manager`, `travel_agent/console.py`): the harness's `serve` always uses `session-manager`, whose agent registry is fixed when it first starts, so on a shared dev server it would show another app's agents.

## Data

- **Seeded inventory, any date** (`travel_agent/travel/inventory.py`): every route and date returns the same planted shape: the cheapest flight has a stop, a slightly dearer nonstop, and a business-class nonstop over $1,000. Flight ids encode route, date and slot, so `find_flight` rebuilds a flight from its id.
- **Money is integer cents throughout.** Cedar has no floats.
- **Bookings say what they buy:** `FlightBookingRequest` carries `date`, `price_cents` and `nonstop`, so a policy can judge them, and `book_flight` refuses a booking whose claims don't match the flight. The policy decides on claims; the tool keeps them honest.
- **Bookings go to a JSON ledger** (`.data/bookings.json`) with deterministic confirmation codes, so a retried booking can't double-book and bookings survive worker restarts.

## Exercises

There is no exercise on prompt injection: `DEMO_INJECTION_SUSCEPTIBILITY` stays on, called out in code and in the assignment: the model is gullible on purpose, and it doesn't matter.

**Exercise 2 ends its durable-session steps with Code Mode and Monty, hands-on** (step 6, about 5 minutes, the AI Agent branch's Tier II; Tier I is the durable session, Tier III governance). The agent's "The agent" section names Code Mode and Monty in a sentence, so the session steps make sense before it. `uv run code-mode` runs `codemode/sandbox.py`, one file: `MODEL_SCRIPT`, marked as the code an LLM writes; `run()`, the few lines of Monty that start a sandbox; and `HOST_FUNCTIONS`. Learners add the model's script (playing the model), then write `run()` and run the script with no host functions, so it's refused (`search_flights` isn't defined: nothing exists in the sandbox), then add `search_flights`, defined on the host and called from the sandbox (three `TODO(ch02)` blocks, graded by exercise 2's check; the site's Insert replaces whichever block a snippet solves) (a fresh sandbox, type-checked against the host's signatures, with a time limit), and nothing else, so the step is about Monty and not the workshop's code. How the agent's workflow plays the host (the approval posture, activities, replay) is in the "The agent" section at the start of the exercise. It's part of exercise 2 rather than an exercise of its own because the course derives chapter numbers from the challenge directories. It needs neither Temporal nor a model.

**No module depends on having done the earlier ones.** A learner who skips ahead, or whose sandbox starts over from its snapshot (every TODO open), shouldn't have to redo anything. A module's `requires` say what it builds on, across branches; `./quest catch-up A8` solves the TODOs of everything A8 builds on, block by block (the authoring markers name the module whose TODO a block is, so N3's TODO stays open beside N2's solved one in the same file), backs up an attempt that was started, and leaves finished work alone (a TODO that's gone is the learner's). The browser course runs it from the runner's poll whenever the exercise on the page changes, including the first poll of a fresh sandbox, and restarts a running worker. Locally, `./quest enter` and `./quest reset` run it. `scripts/verify_modules.py` proves each module's prerequisites are enough: its check passes with only them and it solved.

**Every exercise is tested end to end on the live site.** The course's Playwright tests (`course/e2e/`) start a real sandbox, run each exercise's solve (`./quest solve`) and press its ✓ Check, every day and after every deploy that changes an exercise. They find the exercises in the site's picker and the scripts through the Check button, so a new or changed exercise is covered without editing them, as long as its modules have code checks that their solutions pass. An exercise without a check is only opened. The rest of what the tests depend on, and what to update when it changes, is in [course/DESIGN.md](course/DESIGN.md#keeping-them-in-step-with-the-workshop).

## Verified facts (2026-10-15)

- End to end with the real verifier and the scripted model: Ada's flight, return flight and hotel run unattended in auto mode; Grace's booking isn't permitted (no rule permits it); in the injection session, Mallory's booking isn't permitted and the user's own trip is booked.
- (2026-10-19) With `@on_deny("escalate")` on the booking rules, a booking no rule permits (Mallory's, before any form) comes to a person instead, with the rules' `@reason`: the verifier denies it, the evaluator (`travel_agent/agent/policy.py`) reads the policy file in the `read_policy` activity and escalates, the call stays pending until answered, and a rejection reaches the model.
- With the verifier stopped, an auto-mode call comes to a person immediately.
- A second `tool_approval` for a decided call is rejected with `ToolApprovalAlreadyResolved` (from the client and from `temporal workflow update execute`), and leaves no history event.
- A code-mode script whose host call is refused returns `Script error (MontyRuntimeError: Exception: ToolApprovalDenied: ...)` as its result, not an exception.
- Sending a message to a session with no worker running blocks until a worker accepts the Update.
- The agent's base prompt (system prompt plus tool descriptions) is about 3k tokens: Ollama's default 4k context is too small.
- `gemini-3.8-flash` (2026-10-15, 2 runs of `bench_llm.py`): search 2/2, form 1/2, book 1/2, booking for someone else 2/2, injection 2/2; a whole run of the five walkthroughs took about 5 minutes. When it missed, it searched on assumptions instead of asking for the trip form.
- (2026-10-31) Exercise 3 end to end on `travel-stack up` (Temporal CLI 1.8.3, server 1.31.2) with `gemini-3.8-flash`: the travel agent's script called `ask_concierge`, the concierge's own agent (Gemini, with `get_weather` and `find_events`) answered over Nexus, and `reserve_table` came back with a confirmation from `TableReservation`; `uv run trip-briefing` got its briefing from the same `ask`. The caller's history has `NexusOperationScheduled`/`Started`/`Completed`, and `Started` carries a link to the workflow it started in `concierge`.
- (2026-10-31) With the concierge's worker stopped, the call stays `SCHEDULED` (attempts fail with "upstream timeout") and the session waits; it starts once the worker is back: within seconds after a short outage, about 40 to 55 s after a 90 s one (the server backs off). Capping `component.nexusoperations.retryPolicy.maxInterval` at 5 s didn't shorten it, so it isn't set.
- (2026-10-31) In auto mode, with the live verifier and the regenerated schema: `ask_concierge` runs unattended, and `reserve_table` is refused ("no rule in your policy allows it").
- With the TODO open, `ask_concierge` raises in the workflow, and the script's error goes back to the model (`NotImplementedError: TODO(ch03)…`): the session doesn't wedge.
- Not yet measured: the model on the GPU endpoint. Run `scripts/bench_llm.py` before the first session.
